# Database Migrations

## 1. Overview

The `migrations/` directory contains the migration history generated and maintained by Prisma Migrate.

Database migrations are used to track changes made to the EduMesh database schema over time.

Whenever the database structure changes, a migration can record the required modifications so that the database can be updated in a controlled and consistent manner.

This directory helps maintain database consistency across different development environments and team members.

## 2. Purpose of Migrations

Database migrations are responsible for:

- Tracking changes to the database schema.
- Creating new database tables.
- Modifying existing database columns.
- Establishing and modifying relationships.
- Adding indexes and constraints.
- Removing or updating database structures when required.
- Maintaining a consistent database structure across environments.

## 4. How Prisma Migrations Work

Prisma Migrate manages database schema changes through migration files.

The general workflow is:

1. Modify the database models in `schema.prisma`.
2. Generate a migration based on the schema changes.
3. Review the generated SQL migration.
4. Apply the migration to the development database.
5. Verify that the database structure has been updated.
6. Commit the migration files to Git.

Each migration records a specific change to the database structure.

## 5. Migration Commands

The following Prisma CLI commands will be used during development.

### Create and apply a development migration

```bash
npx prisma migrate dev --name migration_name
```

Creates a migration from the schema changes and applies it to the development database.

### Apply existing migrations

```bash
npx prisma migrate deploy
```

Applies pending migrations in deployment environments.

### Check migration status

```bash
npx prisma migrate status
```

Displays the status of database migrations.

### Generate Prisma Client

```bash
npx prisma generate
```

Generates Prisma Client based on the current Prisma schema.

## 6. Migration Naming Convention

Use descriptive migration names that explain the database change.

Examples:

- `init`
- `add_user_role`
- `create_subject_model`
- `add_resource_approval_status`
- `create_quiz_attempt_model`
- `add_notification_read_status`

Migration names should be concise and meaningful.

Prisma generates the timestamped migration directory names automatically.

## 7. Migration Management Rules

- Every meaningful database schema change must be tracked through migrations.
- Migration files must be committed to Git.
- Review generated SQL before applying important schema changes.
- Do not casually edit migrations that have already been applied and shared.
- Do not delete existing migration history to resolve database issues.
- Keep migrations in chronological order.
- Test migrations in the development environment.
- Coordinate shared schema changes with the backend developer.
- Avoid running development migration commands against production databases.
- Use deployment-safe migration commands in deployment environments.

## 8. Team Collaboration

EduMesh has separate frontend and backend development branches.

The backend developer is responsible for database schema changes and migrations.

When multiple developers work on the database:

- Communicate schema changes before implementation.
- Coordinate migration creation and application.
- Commit migration files alongside related schema changes.
- Avoid conflicting migration histories.
- Verify database consistency after merging changes.

## 9. Relationship with Other Prisma Files

| File or Directory | Responsibility |
|---|---|
| `schema.prisma` | Defines the database schema |
| `migrations/` | Tracks database schema changes |
| `seed.js` | Inserts initial database records |
| `README.md` | Documents Prisma database management |

## 10. Development Workflow

The migration workflow for EduMesh will follow these steps:

1. Identify the required database change.
2. Update `schema.prisma`.
3. Generate a migration.
4. Review the generated SQL.
5. Apply the migration locally.
6. Verify the resulting database structure.
7. Test affected backend functionality.
8. Commit the schema and migration changes.
9. Coordinate the changes with the team.
